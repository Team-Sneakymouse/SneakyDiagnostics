# SneakyDiagnostics Ignite companion

Install `SneakyDiagnostics-Ignite-<version>.jar` in Ignite's `mods/` directory alongside the independently installable Paper plugin in `plugins/`. Restart after installing or replacing the companion. Keep one version of each artifact. Both individual scheduler captures and `/diagnostics all` automatically start and stop the probe; scheduler status shows availability.

## Compatibility

The target is Paper 26.2+, with compilation and runtime verification against Paper 26.2 build 116, Java 25, and Ignite 1.2.1 (Mixin 0.8.7, MixinExtras 0.5.3). There is no exact Minecraft/Paper build-number gate. Recompilation is needed when the required internal scheduler contracts change, rather than for every release. Future releases have not been verified merely because their version is newer.

Structural checks require scheduler/task/future constructors, cancellation methods, the runners map, task class access, async delegation into `CraftTask.run`, callable invocation, pending-queue execution of internal tasks, and listener dispatch through `RegisteredListener.callEvent` into `EventExecutor.execute` (Paper API; `PaperEventManager` calls it for every plugin listener). The tracker send probe additionally requires `ServerEntity.sendChanges()`/`sendDirtyEntityData()`, the `entity` field, `sendChanges` calling `sendDirtyEntityData`, and Moonrise's `ChunkMap.newTrackerTick` calling `ServerEntity.sendChanges`. Required injection counts and Mixin validation add checks during transformation. A mismatch fails startup with an incompatibility error instead of silently producing partial measurements. These checks cannot prove unchanged semantics in a future implementation; run the runtime proof when updating Paper or Ignite. The tick-phase hooks add their own checks (see [Tick phases](#tick-phases)). Velocity activates no scheduler Mixins. Server/loader classes are compile-only and excluded from the artifact. Mixins do not target versioned CraftBukkit packages or anonymous cancellation-runnable class names.

## Measurements and limits

The scheduler report adds an `ignite` section with groups by event, plugin owner, runnable/consumer/callable class, sync flag, and cancellation caller. Events are `creation`, `execution`, `cancel_task_request`, `cancel_plugin_request`, and `deferred_cancel_scan`. Each group has started/completed/throwing counts, total/max nanoseconds, a log2 histogram of completed scope durations (`histogramLog2`, the shared probe's 41 buckets), and first/last observation offsets. Repeated individual cancellation requests are also counted across the capture.

Cancellation wrappers propagate the request's owner/body/caller through an internal queued task, attributing its entire deferred scan when it executes. No anonymous `$2` target is assumed. This measures the main scheduler's deferred scans; separate async scheduler management-executor cancellation scans are not timed by this hook. For cancellation and deferred groups, `sync` describes the target identity; deferred scans themselves execute on the main thread. Unknown targets use an unknown owner/class and a default sync flag, which must not be interpreted as a known sync task.

Execution measures runnable and consumer bodies and the callable invocation, preserving exceptions and return values. Counts describe observed calls, not successfully removed tasks. Timings are inclusive wall time, not CPU time; request, deferred, and execution scopes may overlap and must not be summed. Creation timing covers probe bookkeeping, not registration latency. Cancellation caller is the first external stack frame, not proven plugin ownership. Tasks created before capture may have unknown cancellation identity when no active runner can supply it.

### Listener totals (every call)

`listenerTotals` aggregates every plugin listener call made while recording, per owner plugin x listener class x event class x priority x async flag: calls, inclusive `totalNanos`, server-thread `selfNanos` (nested listener calls subtracted through a depth stack, so self times add up), `maxNanos`, a log2 histogram, and the calls and time on other threads kept apart. A per-second series holds each owner plugin's server-thread total and self time. Bounds: 4,096 keys (later keys counted in `overflow`), 256 owners with a series, nesting tracked to depth 64 (`nestingOverflow`), 192-character labels; any overflow makes the totals and `igniteComplete` incomplete. `slowListeners.observedInvocations` equals the sum of calls plus overflow plus `runningAtStop` when the stop runs on the server thread.

Hot path: the mixin caches each key's slot on its `RegisteredListener` (an `@Unique` field holding a short immutable chain, one entry per event class and async flag that registration received, at most 8), so a steady-state call compares the cached capture and event class, updates plain fields on the server thread and allocates nothing. Only the first call of a key in a capture reads labels, builds the key and takes the totals lock. Calls on other threads update their slot under its lock. The first call of each key includes its lookup in its own time (about a microsecond, once per key and capture).

### Slow calls (when, not only how much)

Groups are whole-capture aggregates. To place time on the timeline, the probe also keeps individual slow calls:

- `slowExecutions`: scheduler scopes (execution, cancellation requests, deferred scans; never creation bookkeeping) of at least 1 ms (`limits.slowNanos`). Each record has the group labels, `startOffsetMicros`/`endOffsetMicros` from the shared capture origin, `nanos` (inclusive wall time), `thread`, `throwing` and `endedAfterDeadline`.
- `slowListeners`: plugin event-listener calls of at least 1 ms: owner plugin, listener class, event class, priority, `asyncEvent`, the same timing fields. `observedInvocations` counts every listener call made while recording. Only one executor call is timed; nested events and anything it opens (an inventory's `InventoryOpenEvent` listeners) are inside its time and also recorded on their own when slow.
- `runningAtStop`: up to 32 scheduler scopes begun but not ended when the capture stopped, with their running time so far (`count` is the total). Completion, this set and the slow list change under one lock, so a call racing the stop is reported either as running or as completed, never neither.
- `slowListeners.runningAtStop` / `runningAroundStop`: listener calls begun but not ended at stop (counted, not listed: tracking each call would cost more than the hook itself), and those enclosing the stop on its own thread (normally SneakyDiagnostics' tick-end listener). A call still running on another thread makes the listener list incomplete. `ServerTickEndEvent` listeners run after Paper measured the tick duration.
- `measuredTicks`: for every server tick (current tick), the interval Paper measured as its duration, taken from the tick's first `ServerTickEndEvent` listener call (Paper reads the duration just before that dispatch) minus `getTickDuration()`. Recording it costs one type check per listener call while recording and one short synchronized append per tick; at most capture seconds x 40 entries, with `dropped` counting the rest. It lets readers exclude tick-end work exactly, even when no listener record of it was kept.

`thread` is `server`, `other` or `unknown` (no server, as in the runtime proof). `tick` is present only for `server`: `Bukkit.getCurrentTick()`, the counter shared-probe reports use and the timeline records as `firstCurrentTick/lastCurrentTick`. It is not the timeline's tick number, which stops while the server pauses when empty (see the schema's tick identity section). Async calls overlap ticks and have no tick identity. Each kind keeps its longest `max(512, 64 x capture seconds)` calls, at most 16,384 (about 3 MB at the cap; 3,840 for a 60 s capture); a longer call replaces the shortest, `observed` counts every call over the threshold and `evicted` those left out, so `complete` is false when the list is partial. Eviction does not change `igniteComplete`, which describes the aggregates. Fast calls cost a clock read on each side and a comparison (listeners: plus two uncontended counters, a thread check, the slot-cache check and the totals update); labels are read and records allocated only for slow calls (and, for listener totals, once per key and capture). Slow records overlap each other and plugin sections, so sum only their union per thread.

State is bounded to 2,048 groups, 100,000 task identities, 100,000 cancellation IDs, up to 16,384 slow scheduler and 16,384 slow listener calls, 4,096 listener keys (41-long histograms each, about 3 MB at the cap) and 256 owner series of two longs per capture second (about 7 MB at 256 owners and 1,800 s), with 192-character labels. Overflow is explicit. In-flight scopes at stop are reported without a completed duration; late completions cannot mutate the detached report. Hooks bypass aggregation outside captures, and recording expires at the requested monotonic deadline even during a stalled tick. Hooks still add an idle branch and cancellation-origin field access. Instrumented execution uses synchronized aggregation and adds overhead, especially under concurrent async load.

### Tick phases

A second local MBean, `com.teamsneakymouse.sneakydiagnostics:type=ServerProbe` (protocol 1, same JDK-values-only rules), serves server-internal probes addressed by name: `start(probe, captureId, startedNanos, seconds)`, `stop(probe, captureId)` returning that probe's map, and `Status` listing every probe (`phases available, idle; tracker recording <id>`). The probes are `phases` and `tracker` (see [Tracker sends](#tracker-sends)); each keeps its own capture, so `/diagnostics all` records both under one capture ID and either collector can run alone. An unknown name fails with `IllegalArgumentException`. `ServerControl.PROBES` is the registry: a further probe joins with one line. Protocol 1 already has this shape: the single-probe signature on the feature branches was never released or deployed. See the [MBean contract](../docs/report-schema-v2.md#ignite-serverprobe-mbean-protocol-1). The plugin's `phases` collector (`/diagnostics phases start`, included in `all`) writes the `phases` probe's result to `phases-1.json`.

For every server tick (current tick, so rows match the timeline's `firstCurrentTick..lastCurrentTick` and Ignite record ticks) the probe stores the exclusive server-thread time of each phase in microseconds. A nested phase is subtracted from its parent, so a tick's phases add up. Hooks (all Mojang-mapped, `remap = false`, call sites wrapped unless noted):

| phase | hook |
|---|---|
| tick row | `MinecraftServer.processPacketsAndTick` head (`runServer` has just set `currentTickStart` and incremented `currentTick`) |
| `tick-start-tasks` | `runAllTasksAtTickStart()` in `processPacketsAndTick` |
| `scheduler` | `CraftScheduler.mainThreadHeartbeat()` (method wrapped) |
| `level.<world>.other` | `ServerLevel.tick(BooleanSupplier)` in `tickChildren`, minus the phases below |
| `level.<world>.entities` | `EntityTickList.forEach` in `ServerLevel.tick` |
| `level.<world>.chunks` | `ServerChunkCache.tick(BooleanSupplier, boolean)` in `ServerLevel.tick`, minus tracker and spawning |
| `level.<world>.tracker` | `ChunkMap.tick()` in `ServerChunkCache.tick` (Moonrise: it only calls `newTrackerTick`) |
| `level.<world>.block-entities` | `tickBlockEntities()` in `ServerLevel.tick` |
| `level.<world>.block-events` | `runBlockEvents()` in `ServerLevel.tick` |
| `level.<world>.spawning.state` | both `NaturalSpawner.createState` calls in `ServerChunkCache.tickChunks` (mob-cap bookkeeping; runs whether or not mobs may spawn) |
| `level.<world>.spawning.spawn` | `NaturalSpawner.spawnForChunk` in `ServerChunkCache.tickSpawningChunk` (only called when a category may spawn) |
| `level.<world>.spawning.custom` | `ServerLevel.tickCustomSpawners` in `tickChunks` (phantoms, patrols, cats, wandering trader, sieges) |
| `connections` | `ServerConnectionListener.tick()` in `MinecraftServer.tickConnection` (player connection ticks, including `ServerPlayer.doTick`; console commands run after it, in `other`) |
| `diagnostics` | `RegisteredListener` executor calls and `CraftTask.run` of SneakyDiagnostics (census slices, timeline sampling, scheduler snapshots, spawn counts) |
| `outside.tick-end` | the `ServerTickEndEvent.callEvent()` dispatch in `tickServer`, where Paper's measured duration is read |
| `outside.diagnostics` | SneakyDiagnostics work during that dispatch or between ticks |

Paper measures a tick from `currentTickStart` (taken at the top of the loop, before `processPacketsAndTick`) to just before the tick-end dispatch, so every in-tick phase lies inside it: `other = measured - phases`, exact in whole microseconds, and `null` for ticks without a measured duration (empty-server pauses, the tick a stop interrupts). The probe reads the measured duration itself (`event.getTickDuration()`), so it does not need the scheduler collector. Natural spawning is also counted per world: `createState` calls, `spawnForChunk` calls, those calls that tried to add at least one entity, the entities `NaturalSpawner.spawnCategoryForPosition` tried to add (before spawn events can cancel them), and custom-spawner calls.

Structural checks (before any mixin applies, and again per target): each wrapped call site exists exactly as often as the mixin's `require`/`allow` (two `createState` calls, one of each other), `runServer` sets `currentTickStart` and increments `currentTick` before `processPacketsAndTick`, tick-start tasks run before `tickServer`, `tickServer` dispatches `ServerTickEndEvent` once and reads `currentTickStart`, and `ChunkMap.tick()` still calls `newTrackerTick`. `PhaseContractTest` runs them against the server JAR. `ChunkMap` is also in the tracker contract (`newTrackerTick` calls `ServerEntity.sendChanges`); both checks run at load, and no mixin transforms it. The mixin config plugin re-verifies each transformed class against every contract that covers it, so a class targeted by both a phase and the tracker hook would have to satisfy both; today none is.

Hot path: each hook reads one volatile field when idle. While recording, the server thread (the thread that started the capture) updates a fixed nesting stack (depth 32) and per-tick accumulators in plain arrays: no lock, no `ThreadLocal`, no allocation; other threads skip the hooks. World slots are cached on each `ServerLevel` per capture (one `getWorld().getName()` per world and capture); listener and task owners are cached on the registration/task (one name comparison each, ever). Recording starts at the tick after `start`, so the first row is a whole tick, and stops opening rows at the deadline.

Bounds: capture seconds x 40 rows (`dropped` counts the rest; totals include them), 64 worlds (later worlds' time stays in their parent phase and they are listed in `omittedWorlds`), nesting depth 32 (`depthOverflow`), and at most 8,000,000 stored values (columns x capacity, 32 MB; a phase beyond that keeps its totals and is listed in `omittedSeries`, which only matters past about 100 phases in a 30-minute capture). Any of these, `nestingErrors` or `spanningTicks` makes the phases incomplete. `stop` must run on the server thread; called elsewhere it discards the phases and says so.

The server classloader owns all probe state. A local Standard MBean, `com.teamsneakymouse.sneakydiagnostics:type=SchedulerProbe`, exposes protocol version 1, status, start, and stop using only JDK values. The plugin accesses it through the platform MBean server without linking companion classes. No remote JMX connector is opened by this project.

### Tracker sends

The `tracker` probe of the `ServerProbe` MBean (registered with the scheduler bridge) wraps `ServerEntity.sendChanges` and, nested in it, `sendDirtyEntityData`. The plugin's `packets` collector starts it on the server thread, which becomes the only thread whose sends are timed; sends on other threads are counted, not timed. Each entity's group (Bukkit entity type and owner hint: `(player)`, `class:<name>` for non-Minecraft entity classes, else sorted PDC namespaces) is resolved the first time a capture sees it and cached on the tracker entry with the capture's generation, so a later capture resolves it again. Idle cost is one volatile read per send. While recording, a send costs two clock reads and a few plain array updates (no locks, no allocation); the first send of each entity in a capture reads its PDC keys once, which makes the capture's first ticks slower on a server with many entities. Recording cost per tick scales with the number of tracked entities that have viewers and has not been measured on a live server. State is bounded to 512 groups (more go to an overflow group) with 192-character labels and one series value per group per capture second. See the [report contract](../docs/report-schema-v2.md#packets-1json-tracker-sends).

## Verification

```powershell
.\gradlew.bat build
.\gradlew.bat :ignite:test -PcompatibilityServerJar=D:/path/to/versions/26.2/paper-26.2.jar
```

The second command verifies scheduler, listener and tick-phase contracts against an extracted server JAR. Use the actual server JAR under `versions/`, not the Paperclip launcher. Contract tests also reject removed methods and changed internal execution paths; probe tests cover caps, attribution, expiration, and report isolation.

For the optional runtime proof, prepare an ignored `.scratch/scheduler-proof/` directory containing `ignite.jar`, a Paper launcher named `paper.jar`, and its matching `cache/`, `versions/`, and `libraries/` directories from an isolated installation. No world, EULA acceptance, server configuration, or listener is needed: the proof uses a custom entrypoint instead of starting Minecraft.

```powershell
.\gradlew.bat :ignite:verifyRuntime
# Or use another prepared directory:
.\gradlew.bat :ignite:verifyRuntime -PruntimeProofDirectory=D:/path/to/proof
```

The task places companion and proof JARs in a dedicated `diagnostics-mods/` folder and uses the freshly built plugin JAR through a separate classloader. Keep that folder reserved for these two JARs. It checks sync/async/consumer/callable execution, checked and unchecked exception preservation (including a listener's `EventException`), individual/plugin/future cancellation, deferred attribution, slow scheduler and listener records, listener totals and group histograms, idle behavior, and bridge communication. It also loads `ServerEntity` so the tracker send hooks are applied by Ignite, and runs an empty tracker capture through the server bridge from the plugin's classloader; it creates no entity (that needs a world), so tracker timing itself is covered only by unit tests. Warm single-thread loops print indicative idle/recording costs for a task run and a listener call; they exclude creation/cancellation and are not a server TPS benchmark. On the development machine (2026-11-09, repeated runs) they printed 20-25 ns idle / 300-450 ns recording per task run and 6-15 ns idle / 50-60 ns recording per trivial listener call, executor included. With listener totals (2026-11-19, three runs each, same machine and session): 11-13 ns idle / 63-73 ns recording per listener call against 11-21 / 54-58 ns for the previous commit, and 83-85 ns when one registration receives two event classes in turn; task runs printed 369-380 ns recording against 281-352 ns. The spread between identical runs is noise of an unpinned loop. This proof does not exercise live command routing or a loaded Minecraft workload.

The proof also defines every tick-phase target (`MinecraftServer`, `ServerLevel`, `ServerChunkCache`, `NaturalSpawner`) through real Ignite/Mixin, so a missing call site fails it, checks the `ServerProbe` MBean (both probes recording one capture ID through JMX, each stopping alone, an unknown probe name rejected), records one tick with a SneakyDiagnostics task nested in the scheduler heartbeat and a SneakyDiagnostics listener (the heartbeat's self time excludes the nested task), and drives the plugin's phases bridge from its own classloader. The server, level and chunk hooks cannot run without a Minecraft server; they use the same frame code as the heartbeat hook. Phase costs (2026-11-19, three runs, median of five alternating rounds each, same machine): a task run or listener call of another plugin 7-8 ns idle and 7-8 ns recording (the owner check), of SneakyDiagnostics 7-11 ns idle and 47-53 ns recording (one phase frame), and an empty scheduler heartbeat 106-256 ns idle against 134-259 ns recording; the heartbeat's own run-to-run spread is larger than its phase frame. Per server tick a recording capture opens about 4 + 8 x worlds frames (a few microseconds at ~40 ns each), plus one per `spawnForChunk` call and per SneakyDiagnostics call.
